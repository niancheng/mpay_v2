# 重复支付请求兼容（store-bill-1.2.1）

同一商户、同一商户订单号经过原有鉴权后，先校验业务参数，再恢复已有支付单。页面提交和 API 下单共用此规则；无需修改 dujiaonext。

## 行为边界

- 待支付、支付中及结果未知：只读恢复原支付单；不重新选路、调用插件、预占门店金额、冻结服务费、增加尝试次数或延长有效期。
- 首次下单尚未返回付款资料：返回本站原支付页。等待页只读查询资料是否就绪，状态仍为支付中时也可恢复显示。网络失败不重发支付。
- 成功、关闭、超时或实际付款窗口已结束：返回原单结果，不下发旧付款二维码。只读检查不伪造终态或提前释放资金。
- 明确失败：保留原失败重试开关及次数上限。恢复原单不算新尝试；允许的失败重试才创建下一张支付单。
- 金额按业务单原始金额比较，不与浮动后的实付金额混淆。商品信息、通知/返回地址、业务扩展字段、明确指定的支付方式/通道及支付身份有冲突时继续拒绝；IP、设备和 page/api 入口变化不覆盖原单快照。
- 凭证、验签、商户权限和 V2 时间戳校验不变；不同协议版本不隐式转换原订单的回调签名协议。
- `active_pay_no` 在终态被清空后按历史支付单恢复，成功订单只选择真实成功的尝试。损坏或跨商户/跨业务引用拒绝自动重建。

## 实现

公共发起层区分 `created` / `reused`，只允许创建者派发插件。业务单行锁、已有唯一索引和创建事务内复查共同防止重复建单。仅对指定商户订单唯一键竞争重读，其他 SQL 错误照常失败；保留门店 guard 的锁顺序及事务外外呼边界。

V1/V2 继续使用现有协议组装和验签流程。资料缺失时由共享复用服务提供合法、仅用于本次响应的 `jump` 承接结果；不把回跳自身的材料持久化到订单。V2 响应仍重新签名，付款码模式仍返回状态摘要。

收银台前端仓库只包含编译产物，因此通过独立的 `payment-reentry.v1.js` 补齐等待态恢复，不手改压缩包。只在实际显示等待页时 GET 原单详情，资料就绪后最多自动刷新一次；存储受限或重复刷新时提供手动刷新入口。

## 验证与升级

新增 `payment_reuse.php`（真实 MySQL、签名 V1/V2、状态与参数边界）、`payment_reuse_concurrency.php`（多进程同号、同号金额冲突、慢派发时重入、单次冻结与外呼）、等待脚本单元测试和实际收银台 Chromium 桌面/手机视口回归。原金额分配、回调、并发及容器数据/JWT 升级测试继续执行。

测试使用专用 `mpay_test_*` 数据库和模拟到账数据，不会向真实支付宝发起付款；浏览器测试所有支付 API 均为本地测试数据，外部网络请求被阻断。

无新配置项、无数据库迁移，不要求清理 Redis、删除订单或修改 dujiaonext。更新镜像后重建 mpay 容器及使用同镜像的常驻任务，保留现有数据卷、环境变量和商户密钥。上线验收应使用尚未过期的待支付单执行“进入支付页 → 返回 → 再支付”，核对原支付单号、金额、备注与有效期不变。
